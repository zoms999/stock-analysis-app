이전 설계안에서는 **관리자(Admin) 기능이 로직상으로는 존재하지만(승인, 토너먼트 생성 등), DB 테이블 명세에는 명시적으로 ‘관리자 여부’를 구분하는 컬럼이 빠져 있었습니다.**

Supabase는 클라이언트에서 DB에 직접 접근하는 경우가 많으므로, 보안을 위해 **관리자 권한을 명확히 구분하는 컬럼과 정책(RLS)**이 필수적입니다.

기존 설계에 **관리자 기능을 완벽하게 추가하기 위한 보완 설계안**을 제안합니다.

---

## 1. Profiles 테이블 수정 (관리자 식별자 추가)

기존 `profiles` 테이블에 관리자 권한을 나타내는 컬럼을 추가해야 합니다. 단순히 `user_level` (1~10등급)로 관리자를 처리하면, VIP 유료 회원과 운영자가 섞일 위험이 있으므로 **별도 컬럼으로 분리**하는 것이 안전합니다.

```sql
-- 1. 관리자 권한 컬럼 추가
ALTER TABLE public.profiles 
ADD COLUMN is_admin BOOLEAN DEFAULT FALSE;

-- 2. 관리자 코멘트 (운영자가 유저에 대해 메모할 내용)
ALTER TABLE public.profiles 
ADD COLUMN admin_memo TEXT;

-- (선택 사항) 최고 관리자와 일반 운영자(부운영자)를 나누고 싶다면 ENUM 사용
-- CREATE TYPE admin_role AS ENUM ('NONE', 'MODERATOR', 'SUPER_ADMIN');
-- ALTER TABLE public.profiles ADD COLUMN admin_type admin_role DEFAULT 'NONE';
```

## 2. Admin Audit Log (관리자 활동 로그) **[중요]**

포인트 지급, 환전 승인, 토너먼트 결과 입력 등 돈과 관련된 기능이 많으므로, **"누가, 언제, 무엇을 변경했는지"** 기록하는 감사 로그(Audit Log) 테이블이 필수입니다.

```sql
CREATE TABLE public.admin_logs (
  id BIGINT GENERATED BY DEFAULT AS IDENTITY PRIMARY KEY,
  admin_id UUID REFERENCES public.profiles(id) NOT NULL, -- 작업을 수행한 관리자
  target_user_id UUID REFERENCES public.profiles(id), -- 대상이 된 유저 (있을 경우)
  
  action_type VARCHAR(50) NOT NULL, -- 예: 'POINT_GRANT', 'WITHDRAW_APPROVE', 'BAN_USER'
  target_table VARCHAR(50), -- 예: 'point_transactions', 'users'
  
  details JSONB, -- 변경 전/후 데이터나 상세 사유 (예: "{amount: 1000, reason: '이벤트 당첨'}")
  ip_address TEXT, -- 보안용 IP 기록
  
  created_at TIMESTAMPTZ DEFAULT NOW()
);
```

## 3. 관리자 기능을 위한 RLS (보안 정책) 설정 예시

Supabase에서는 데이터베이스 레벨에서 **Row Level Security (RLS)**를 걸어두어야 해킹을 방지할 수 있습니다. 관리자만 수행할 수 있는 정책을 다음과 같이 설정합니다.

**Q. 관리자는 어떻게 설정하나요?**
초기 세팅 시, Supabase 대시보드(Table Editor)에서 개발자의 계정(row)을 찾아 `is_admin` 값을 `TRUE`로 직접 수정해주면 됩니다.

### 예시 1: 관리자만 포인트 수동 지급/승인 가능
```sql
-- 포인트 테이블 RLS 활성화
ALTER TABLE public.point_transactions ENABLE ROW LEVEL SECURITY;

-- 1. 일반 유저: 본인의 내역만 조회 가능 (SELECT)
CREATE POLICY "Users can view own points" ON public.point_transactions
FOR SELECT USING (auth.uid() = user_id);

-- 2. 일반 유저: 시스템에 의한 자동 적립/사용만 가능 (INSERT - 보통은 서버 사이드에서 처리하므로 막아둠)
-- (서비스 구조상 클라이언트 직접 INSERT를 막고 Edge Function을 쓰는 것을 권장)

-- 3. 관리자: 모든 내역 조회 및 수정 가능 (ALL)
CREATE POLICY "Admins can do everything on points" ON public.point_transactions
FOR ALL USING (
  EXISTS (
    SELECT 1 FROM public.profiles
    WHERE id = auth.uid() AND is_admin = TRUE
  )
);
```

## 4. 기획서의 '관리자 기능' 매핑

기획서에 명시된 기능들이 DB상에서 관리자에 의해 어떻게 처리되는지 정리했습니다.

### 4.1. 포인트 관리 (승인 및 회수)
*   **상황:** 유저가 출금 신청을 함 -> `point_transactions`에 `is_approved = FALSE` 상태로 저장됨.
*   **관리자 액션:** 관리자 페이지에서 미승인 목록 조회 -> 검토 후 `is_approved = TRUE`로 업데이트.
*   **SQL:**
    ```sql
    UPDATE public.point_transactions
    SET is_approved = TRUE, description = '관리자 승인 완료'
    WHERE id = [Transaction ID];
    
    -- 동시에 로그 남기기
    INSERT INTO public.admin_logs (admin_id, action_type, details)
    VALUES (auth.uid(), 'APPROVE_POINT', '{"tx_id": ...}');
    ```

### 4.2. 토너먼트 관리 (승자 처리)
*   **상황:** `KOSPI 소수점 맞추기` 이벤트 종료 시간 도래.
*   **관리자 액션:** 실제 KOSPI 종가를 확인하고 시스템(또는 관리자)이 정답자를 필터링.
*   **DB 처리:**
    1.  `tournaments` 테이블의 `status`를 `SETTLED`로 변경.
    2.  `tournament_entries` 테이블에서 정답자와 가장 가까운 유저 조회.
    3.  해당 유저에게 리워드 지급 (`point_transactions` INSERT).

### 4.3. 파트너 정산
*   **상황:** 파트너 유저가 이번 달 수익금 정산을 요청.
*   **관리자 액션:** `partner_settlements` 테이블 조회 후 실제 송금 진행 -> DB에서 `is_paid = TRUE`로 변경.
